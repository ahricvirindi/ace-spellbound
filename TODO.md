## Achievement system
- [ ] **Wire the remaining `SpellboundEventTrigger` values.** Wired today: `Player_OnKill`, `Player_OnLevel`, `Player_OnDeath`, `Player_PreCast`. Roughly 22 enum values still unwired (regen events, portal entry/exit, loot, quests, item use, magic resist, evades, PK kill/death, account create/login, etc.). Bulk expansion deferred — pick this up one trigger at a time when an achievement requires it. Pattern: add payload under `Model/Events/Payloads/`, register in `EventBus._payloadFor`, drop a `<Trigger>Handler.cs` under `EventHandlers/AchievementRules/`.
- [ ] **Add NPC-commerce triggers.** Three new `SpellboundEventTrigger` values that don't exist in the enum yet:
  - `Player_OnGiveItemToNpc` — postfix on `Player.HandleActionGiveObjectRequest` (or whichever method finalizes the give). Payload captures Giver, Receiver (the NPC), the item (Wcid + Name), and StackSize. Useful for quest turn-in achievements ("donate 100 trophies to X") and emote-tied content.
  - `Player_OnSellItemToNpc` — postfix on the vendor sell path (`Player.HandleActionSellItem` / `Vendor.SellItemsValidate` — needs a small spike to find the right method). Payload: Seller, Vendor, items + sale value. Powers "spend X selling to vendors" / "sell rare items" leaderboards.
  - `Player_OnBuyItemFromNpc` — symmetric to the sell path. Payload: Buyer, Vendor, items + purchase value. Powers "lifetime spend at vendors" leaderboards.
  - For all three: same wiring pattern as existing triggers (enum value, payload record under `Model/Events/Payloads/`, register in `EventBus._payloadFor`, `<Trigger>Handler.cs` under `EventHandlers/AchievementRules/`). Pick enum numeric IDs above the current max so they don't collide with retired values.
- [ ] **Multiplier-style award types.** `ExperienceBonus`, `LuminanceBonus`, `FlatDamage`, `PercentDamage`, `FlatCritDamage`, `PercentCritDamage`, `ArmorLevel`, `AllResists` — `AchievementService.ApplyToCharacter` currently logs and skips them. Each needs a dedicated runtime calc-path Harmony hook (XP grant path, damage calc, etc.) since they're per-event multipliers, not one-shot stat mutations. Decide which calc paths to patch before picking this up.
- [ ] **Season-end "Season X" achievement.** At the end of every season, every account that has at least one non-deleted character earns a per-season commemorative achievement. Implementation choices:
  - **Catalog rows** — one `Achievements` entry per season (IDs starting at 9100 to leave room: `Season 1 Champion = 9100`, `Season 2 Champion = 9101`, etc.). Pick a small symbolic award (e.g. `AwardType=Mana, AwardValue=5`, or zero-bonus and treat the badge itself as the reward). Stable IDs because `AccountAchievements.AchievementId` references them forever.
  - **Granting path** — two reasonable shapes, pick at impl time:
     - SQL operation script under `Database/Spellbound/Operations/season-end-achievements.sql` — `INSERT IGNORE INTO AccountAchievements ... SELECT DISTINCT account_Id ... FROM ace_shard.character WHERE is_Deleted = 0`. Fast, transactional, no server required. Mirrors how `season-wipe.sql` is structured.
     - Admin slash command `/grant-season-achievement <season-number>` that iterates `AccountManager` and calls `AchievementService.TryAwardAtomic` per account. More auditable, runs while the server is up.
  - **Ordering** — must run BEFORE `season-wipe.sql` truncates `character`. Otherwise the "had a character at season end" set is empty. Document the ordering in `season-wipe.sql`'s header comment (currently lists step 1 = ReservedNames snapshot, step 2 = shard truncate, step 3 = spellbound resets — insert "step 0: grant season-end achievements" before step 1).
  - **Idempotency** — re-running must be safe. The existing unique index `(AccountId, AchievementId)` on `AccountAchievements` makes `INSERT IGNORE` (or `TryAwardAtomic`'s race-aware path) the right primitive.
  - **Bonus application timing** — `AchievementService.ApplyToCharacter` runs the per-character bonus walk on grant, but at season-end the characters are about to be wiped. Skip the apply walk for season-end grants OR rely on `PlayerOnEnterWorldHandler`'s login safety net to re-apply on the next-season character. Latter is simpler.

## Account approval gating
Newly-created accounts default to **unapproved** until an admin flips the bit (see Phase 4 admin UI). Unapproved accounts can play but with two restrictions enforced by the mod:
- [ ] **Block chat for unapproved accounts.** Harmony-prefix-cancel the relevant `ChatPacketHandler` / `Player.HandleActionTalk` family methods (whatever the chat send paths are — needs a small spike to find them). When cancelled, send a system tell to the player explaining the account is pending approval. Applies to general, LFG, allegiance, fellowship, /tell — basically any outbound channel. Local-only chat (Player.HandleActionTalk private speech) might be OK to leave through; decide at impl time.
- [ ] **Cap progression at level 10.** Hook into `Player.CheckForLevelup` (we already have a prefix+postfix `__state` pattern there for `PlayerOnLevelHandler`). When the would-be new level exceeds 10 AND the account is unapproved, hold the level at 10 and absorb the excess XP back into `AvailableExperience` so the player doesn't lose accumulated XP. Friendly tell on the rejected level-up.
- [ ] **Schema.** Add an `IsApproved` + `ApprovedAt` + `ApprovedByAccountId` + `ApprovalReason` column to the existing `AccountVerifications` table OR (cleaner if Discord verification semantics differ enough) a separate `AccountApprovals` table. Default `IsApproved = 0` for any account that doesn't have a row. Updates + Baseline + Reset mirrors per CLAUDE.md.
- [ ] **Bypass for elevated accounts.** Don't gate Sentinel / Envoy / Developer / Admin accounts even if their approval row hasn't been set — `AccessLevel > Player` should short-circuit both the chat block and the level cap.

### Event channel
- [ ] Leaderboard counters need a separate dispatch path that subscribes to the same `SpellboundEventTrigger` events as achievements. Two reasonable shapes — pick at impl time:
- [ ] Extend `SpellboundDispatcher.Run` with a 4th step calling `LeaderboardService.RecordEvent(payload)`. Keeps primary dispatch consolidated.
- [ ] Parallel `[SpellboundEvent]` subscribers under `EventHandlers/LeaderboardRules/<Trigger>Handler.cs`, mirroring `AchievementRules/`. Truly independent dispatch (this is one of CLAUDE.md's "earn its own subscriber" exceptions).

**Schema:** `Leaderboards (Category VARCHAR, CharacterId BIGINT, CharacterName VARCHAR, Count INT, SnapshottedAt DATETIME)` with unique index on `(Category, CharacterId)`. Categories are free-form strings the rule author picks (e.g. `kills.virindi`, `kills.pk`, `deaths.pvp`, `achievements.earned`). On each event the channel does an atomic UPSERT: bump `Count`, set `SnapshottedAt = NOW()`, refresh `CharacterName` (in case of rename). All work goes through `RunDbWork` so the tick thread never blocks on the leaderboard DB write.

**Season behavior:** Truncated on season reset. Add `TRUNCATE Leaderboards;` to `Database/Spellbound/Operations/season-wipe.sql`.
